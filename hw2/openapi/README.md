# Контракт Marketplace API

Команды запуска и проверки: [основной README](../README.md).
Ниже — подробности самого контракта и реализации.

`marketplace.yaml` — исходное описание HTTP API в формате OpenAPI 3.0.3.
Формат записи — YAML: отступы задают вложенность, `-` обозначает элемент списка.
Файл хранится в Git и редактируется вручную. Из него OpenAPI Generator создаёт
маршруты FastAPI, базовые API-классы и модели Pydantic в `generated/src`.
Сгенерированные файлы не редактируются и не добавляются в Git.

## Что находится в файле

| Раздел | Назначение |
| --- | --- |
| `openapi` | Версия стандарта описания API. |
| `info` | Название и версия нашего API, общие правила и допущения. |
| `tags` | Группы методов: Health, Auth, Products, Orders, PromoCodes. |
| `security` | Требование Bearer access JWT по умолчанию. |
| `paths` | URL, HTTP-методы, запросы, ответы, ошибки и правила доступа. |
| `components.securitySchemes` | Способ передачи JWT. |
| `components.parameters` | Переиспользуемые параметры UUID, пагинации и фильтров. |
| `components.headers` | Заголовок ответа `X-Request-Id`. |
| `components.responses` | Общие ответы об ошибках с примерами. |
| `components.schemas` | Структуры запросов и ответов, типы и ограничения полей. |

`$ref: '#/components/schemas/ProductCreate'` означает ссылку на схему
`ProductCreate` в этом же документе. `operationId: create_product` задаёт
имя операции для генерации Python-метода. `required` внутри объекта перечисляет
обязательные поля; `requestBody.required` требует тело запроса целиком.
`nullable: true` разрешает значение `null` и не означает необязательность поля.

Например, контракт `POST /products` задаёт следующую цепочку:

1. Клиент передаёт JSON по схеме `ProductCreate` и access JWT.
2. Сгенерированный маршрут принимает запрос и вызывает реализацию API.
3. Реализация проверяет роль, создаёт товар и возвращает `ProductResponse`.
4. Успех — HTTP 201, ошибки имеют общую схему `ErrorResponse`.

Контракт позволяет генерировать интерфейсы и документацию. CRUD товаров,
JWT, роли, создание, чтение, обновление и отмена заказа, а также HTTP-создание
промокодов реализованы в `app/`.
Описания и расширение `x-roles` сами по себе не обеспечивают авторизацию.

## Операции

Всего описано 14 операций:

- `GET /health`;
- `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`;
- `POST /products`, `GET /products`;
- `GET /products/{id}`, `PUT /products/{id}`, `DELETE /products/{id}`;
- `POST /orders`, `GET /orders/{id}`, `PUT /orders/{id}`;
- `POST /orders/{id}/cancel`;
- `POST /promo-codes`.

Только health-check и методы `/auth/*` публичны. Все остальные требуют access
JWT. Роли и правила владения описаны для каждого метода по матрице задания.
Методы оплаты, доставки и произвольной смены статуса не добавлены: их маршруты
в задании не определены. Модель состояний описана в `OrderStatus`.

## Принятые решения

- Все идентификаторы — UUID. Даты передаются с часовым поясом; примеры используют UTC.
- `PUT /products/{id}` полностью заменяет редактируемые поля. Пропущенное
  `description` становится `null`. Владелец при обновлении не меняется.
- При создании товара `seller_id` по умолчанию равен текущему пользователю.
  SELLER может указать только себя; ADMIN может выбрать существующего продавца
  или администратора. Проверка получателя выполняется в реализации.
- Список товаров включает все статусы. Фильтры применяются совместно,
  категория сравнивается точно с учётом регистра. Сортировка — `created_at ASC, id ASC`.
- После мягкого удаления товар остаётся доступен для чтения. Повторная архивация
  существующего товара возвращает 204 без тела.
- Публичная регистрация создаёт USER. SELLER и ADMIN будут добавляться начальными
  данными. Самостоятельно передать роль при регистрации нельзя.
- Access JWT действует 30 минут, refresh JWT — 14 дней. Refresh возвращает только
  новый access token; ротация refresh в текущем контракте не предусмотрена.
- Повторяющиеся `product_id` в одном запросе заказа запрещены: HTTP 400,
  `VALIDATION_ERROR`. Одного `uniqueItems` для такого правила недостаточно.
- Промокоды глобальные, без привязки к продавцу. `valid_until > valid_from`
  проверяется в реализации как межполевая валидация.
- Цены, суммы и скидки передаются JSON-числами с точностью до 0.01. Денежные
  значения должны помещаться в DECIMAL(12,2), переполнение отклоняется без записи.
  В бизнес-логике используется Decimal, скидка округляется ROUND_HALF_UP.
- При явной замене состава заказа снимки цен берутся из текущих цен каталога.
  Само изменение каталога существующие заказы не пересчитывает.
- Лимит операций применяется к действующему пользователю из JWT `sub`.
  CREATE_ORDER и UPDATE_ORDER имеют независимые интервалы.

## Неоднозначности задания

В контракте зафиксированы следующие правила расчётов:

1. Процент до 70 включительно применяется как скидка. При проценте больше 70
   скидка нулевая и цена полная, по фразе задания «в ином случае цена 100%».
2. Если при обновлении сумма стала ниже минимума промокода, скидка снимается и
   использование возвращается, как прямо требует задание. Истёкший или отключённый
   промокод даёт 422 с откатом обновления.
3. При повторной проверке лимита промокода учитывается уже занятое этим заказом
   использование. Обновление не расходует промокод повторно.

## Проверка и генерация

Из папки `hw2`, при запущенном Docker Desktop:

```powershell
docker compose --profile tools run --rm codegen validate -i /workspace/openapi/marketplace.yaml
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\generate.ps1

```

Затем проверьте `http://localhost:8000/health` и `http://localhost:8000/docs`.
Swagger UI, построенный FastAPI по маршрутам, сверяется с исходным контрактом тестами.

## Шаблоны и проверки сгенерированного API

В `generator-config.yaml` задан `templateDir: openapi/templates`. Поэтому команды
генерации выполняются из `hw2`; Docker-сервис codegen и стадия Docker-сборки
используют рабочую папку `/workspace`. Шаблоны хранятся в Git и одинаково
применяются при отдельной генерации и при сборке приложения.

Шаблоны исправляют ограничения используемого python-fastapi генератора 7.12.0:

- Все поля `number` данного контракта генерируются как `Decimal` с границами
  и `multipleOf` из спецификации. JSON-строки и boolean вместо денег запрещены.
- UUID-поля и UUID в пути генерируются как `UUID`.
- Верхние границы stock/page/size соответствуют int32; текстовые поля товаров
  и фильтр category запрещают NUL до обращения к PostgreSQL.
- `additionalProperties: false` превращается в `extra="forbid"`.
- Обязательное тело не имеет значения по умолчанию `None`.
- Параметры Query объявлены через `Annotated`: целые строковые значения
  преобразуются в int, границы проверяются; `page=1.0` не принимается.
- Успешные HTTP-статусы устанавливаются явно по контракту; DELETE возвращает
  204 без тела. Для каждой операции используется один основной успешный ответ.
- Проверенный `TokenModel` передаётся в конструктор реализации API. Расширение
  `x-resource-location` задаёт `Location` при создании товара.
- Разрешённые роли берутся из `x-roles` и проверяются до вызова реализации API.
  `TokenModel` с обязательными `sub` и `role` генерируется через `extra_models.mustache`.
- `x-unique-by: product_id` на массиве позиций заказа генерирует проверку
  уникальности UUID товара, в том числе при разном регистре исходной строки.

`app/contract_http.py` читает дробные JSON-числа сразу как Decimal. Ответы
сериализуются через simplejson без промежуточного float: деньги остаются
JSON-числами. Реализация API возвращает сгенерированный DTO, а общий слой
проверяет ответ и устанавливает HTTP-статус. Для DELETE реализация возвращает None.
Для сериализации DTO вне HTTP можно использовать `to_json()` и `to_dict()`.

`app/main.py` подключает обработчики входных ошибок: HTTP 400,
`VALIDATION_ERROR`, `details.fields`. Ошибки проверки ответа остаются серверными
500. Для всех ответов формируется X-Request-Id. Полное JSON-логирование запросов
относится к следующему этапу. Автоматические 422 в документации заменены
контрактным описанием 400; явные бизнес-ответы 422 для промокодов сохраняются.

## Единый механизм ошибок

`app/errors.py` содержит обычное исключение `AppError`. В сервисах выбрасывай его
для ожидаемых ошибок, указывая код из сгенерированного `ErrorCode`, публичное
сообщение, HTTP-статус и при необходимости словарь `details`:

```python
from app.errors import AppError

if product is None:
    raise AppError("PRODUCT_NOT_FOUND", "Товар не найден", 404)
```

Обработчики в `app/middleware/error_handlers.py` уже подключены через
`install_contract_handlers` в `app/main.py`. Они создают сгенерированный
`ErrorResponse`; вручную писать DTO ошибок не требуется. Отсутствующий `details`
не включается в JSON.

| Код | HTTP |
| --- | --- |
| `VALIDATION_ERROR` | 400 |
| `PRODUCT_NOT_FOUND` | 404 |
| `ACCESS_DENIED` | 403 |
| `TOKEN_INVALID`, `TOKEN_EXPIRED` | 401 |
| `INTERNAL_ERROR` | 500 |

Проверка JWT выбрасывает `AppError` с нужным кодом, чтобы отличать истёкший токен
от невалидного. Сам обработчик ошибок токены не проверяет.
Сообщения и `details` ожидаемых ошибок возвращаются клиенту, поэтому в них
нельзя помещать SQL, пароли и другие внутренние данные.

Не перехватывай все ошибки БД как ошибки валидации. Неизвестные исключения,
включая ошибки соединения и ограничений БД без специального бизнес-разбора,
логируются с классом исключения и местами в стеке без SQL/параметров и возвращают
`500 INTERNAL_ERROR` с общим сообщением.
Каждый ответ содержит `X-Request-Id`.
Ошибки маршрутизации также используют ErrorResponse: NOT_FOUND для 404,
METHOD_NOT_ALLOWED для 405 с сохранением Allow. Другие HTTP-ошибки получают HTTP_ERROR.

## CRUD товаров

В `app/main.py` зарегистрирован `ProductsApi`, наследующий сгенерированный
`BaseProductsApi`. Его методы передают операции в `ProductsService`, а сервис
использует `ProductsRepository` для параметризованных SQL-запросов.

| Метод | Поведение |
| --- | --- |
| `POST /products` | `INSERT RETURNING`, 201, DTO с id/датами БД и заголовок `Location`. |
| `GET /products/{id}` | 200 для любого статуса товара; 404, если товара нет. |
| `PUT /products/{id}` | Полная замена редактируемых полей; пропущенное description становится null. |
| `GET /products` | page=0, size=20, точные фильтры status/category, сортировка created_at/id ASC. |
| `DELETE /products/{id}` | Архивация без удаления строки, повторная архивация — 204 без тела. |

Неверные UUID, JSON, тело и query-параметры отклоняются с 400 до обращения
к БД. В ошибках поля представлены как `price`, `id`, `page` или
`items[0].quantity`; входные данные и внутренние объекты исключений не копируются.

Текущий пользователь определяется по `sub` из проверенного токена. Его роль
считывается из таблицы `users` в транзакции. SELLER создаёт свои товары и меняет
только свои; ADMIN может выбрать существующего SELLER/ADMIN и менять любые товары.
USER может читать, но не создавать/изменять/архивировать товары.

Каждая операция использует `engine.begin()`: успех фиксирует изменения,
исключение откатывает их. Перед изменением товар блокируется через `FOR UPDATE`,
а ответ проверяется сгенерированным DTO до commit. `updated_at` изменяет триггер
из V3. Для списка CTE вычисляет товары и totalElements одним SQL-запросом,
включая пустую страницу за пределами выборки.
Синхронная операция целиком выполняется через `run_in_threadpool`, чтобы
не блокировать обработку остальных HTTP-запросов.
См. [транзакции SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/connections.html#connect-and-begin-once-from-the-engine).

Зависимость `get_token_BearerAuth` из версионируемого `security_api.mustache`
подключает настоящую проверку JWT из `app/security/dependencies.py`.
В приложении нет переключателя входа под произвольным пользователем.

## JWT и роли

`AuthApi` зарегистрирован в `app/main.py`. Все запросы и ответы используют
сгенерированные DTO. Хеширование паролей и операции с синхронной БД выполняются
в рабочем потоке.

| Метод | Поведение |
| --- | --- |
| `POST /auth/register` | Создаёт только USER, возвращает 201 с id/username/role. Повторный username — 409 USER_ALREADY_EXISTS. |
| `POST /auth/login` | Проверяет пароль, возвращает access на 30 минут и refresh на 14 дней. Неверные данные — 401 INVALID_CREDENTIALS. |
| `POST /auth/refresh` | Принимает refresh в JSON и возвращает новый access. Ошибки refresh — 401 REFRESH_TOKEN_INVALID. |

Пароли хешируются Argon2id через `argon2-cffi` с отдельной случайной солью.
В ответах и JWT нет паролей и хешей. Проверка неизвестного username также
выполняет проверку хеша; публичная ошибка одинакова для неизвестного имени
и неверного пароля. См. [документацию Argon2](https://argon2-cffi.readthedocs.io/en/stable/howto.html).

JWT подписываются HS256 через PyJWT. Алгоритм фиксирован в серверном коде;
проверяются подпись, issuer, audience, exp/iat, UUID в sub/jti, роль и назначение
`token_type`. Refresh вместо access отклоняется, в том числе если он уже истёк.
Невалидный access даёт TOKEN_INVALID, просроченный — TOKEN_EXPIRED, оба с 401
и заголовком `WWW-Authenticate: Bearer`.
См. [проверку JWT в PyJWT](https://pyjwt.readthedocs.io/en/2.10.1/usage.html).

При каждом защищённом запросе проверяется существование пользователя в БД
и совпадение его текущей роли с JWT. После удаления пользователя access и refresh
не принимаются. После смены роли старый access становится недействительным;
refresh выдаёт новый access с текущей ролью. Ротации refresh и logout в текущем
контракте нет: refresh можно использовать повторно до истечения его срока.
Отдельная таблица сессий при этой реализации не нужна.

| Операция | USER | SELLER | ADMIN |
| --- | --- | --- | --- |
| Чтение товаров | Все статусы | Все статусы | Все статусы |
| Создание товара | 403 | Только от своего имени | От своего имени или существующего SELLER/ADMIN |
| Изменение/архивация товара | 403 | Только свои | Любые |
| Создание заказа | От своего имени | 403 | От своего имени |
| Чтение/изменение/отмена заказа | Свои | 403 | Любые, с теми же правилами состояния |
| Создание промокодов | 403 | Роль разрешена | Роль разрешена |

Проверка ролей для всех маршрутов заказов и промокодов уже действует.
Все операции с заказами и HTTP-создание промокодов реализованы.
Для чтения/изменения/отмены заказа вызывается `require_order_owner`
из `app/security/authorization.py`: чужой заказ USER даёт
ORDER_OWNERSHIP_VIOLATION, SELLER — ACCESS_DENIED, ADMIN проходит проверку.
Идентификатор владельца нового заказа берётся из проверенного `TokenModel.sub`.

### Запуск и тестовые учётные записи

Из `hw2` выполни:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\init-env.ps1
docker compose up --build -d
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\seed.ps1
```

Первая команда создаёт `.env` при его отсутствии и записывает случайный
`JWT_SECRET`. Ключ не печатается, валидный существующий ключ сохраняется.
`.env` исключён из Git. Compose требует этот ключ; в приложении нет общего
секрета по умолчанию. После изменения ключа нужно пересоздать контейнер api.

Последняя команда запрашивает пароль длиной 8–128 символов без отображения
на экране и создаёт `demo_user`, `demo_seller`, `demo_admin` с соответствующими
ролями. Она вызывается явно и не запускается вместе с API. Повторный запуск
не меняет существующие пароли; если имя занято пользователем другой роли,
команда откатывает изменения. Через публичную регистрацию получить ADMIN нельзя.

Открой `http://localhost:8000/docs`, вызови `POST /auth/login`:

```json
{
  "username": "demo_seller",
  "password": "пароль, введённый при запуске seed.ps1"
}
```

Скопируй `access_token`, нажми **Authorize** и вставь токен без префикса Bearer.
Теперь можно создавать товары через `POST /products`. С токеном `demo_user`
создание вернёт 403, с токеном `demo_admin` можно менять любой товар.
Для `/auth/refresh` передай `refresh_token` в JSON-теле.

## Создание заказа одной транзакцией

`OrdersApi` зарегистрирован в `app/main.py`. `POST /orders` вызывает
`OrdersService.create_order` в рабочем потоке; все изменения выполняются
в одном `engine.begin()`. user_id берётся из проверенного JWT `sub`:
даже ADMIN создаёт заказ от своего имени. Поля user_id и price_at_order
в запросе запрещены.

Проверки и изменения выполняются в следующем порядке:

1. Проверка последней успешной CREATE_ORDER по текущему пользователю.
2. Проверка собственного заказа CREATED или PAYMENT_PENDING.
3. Существование и ACTIVE-статус всех товаров.
4. Проверка всех остатков; в INSUFFICIENT_STOCK возвращается полный список
   проблемных товаров в details.products с requested/available.
5. Резервирование остатков и фиксация цен из заблокированных строк товаров.
6. Расчёт суммы до скидки через Decimal и проверка диапазона DECIMAL(12,2).
7. Проверка промокода: active, счётчик использований, включительный период
   valid_from..valid_until, затем min_order_amount относительно суммы до скидки.
   Для PERCENTAGE применяется процент до 70 включительно; при большем проценте
   скидка нулевая. Для FIXED_AMOUNT предел — сумма заказа. Скидка округляется
   ROUND_HALF_UP до двух знаков. Сохраняются сумма
   скидки и итоговая сумма; current_uses увеличивается один раз.
8. Запись заказа CREATED, позиций с price_at_order и операции CREATE_ORDER.
   Сгенерированный OrderResponse проверяется до commit, ответ — 201.

Повторяющиеся product_id отклоняются моделью до вызова сервиса. Переполнение
денежного диапазона возвращает 400 VALIDATION_ERROR. Ошибка промокода после
резервирования возвращает 422 и откатывает остатки. Поздняя ошибка БД или
проверки ответа возвращает 500 и также откатывает всё, включая использование
промокода и запись в user_operations. Неудачная попытка не создаёт cooldown.

Конкурентные запросы одного пользователя сериализуются блокировкой его строки
FOR UPDATE. Товары блокируются FOR UPDATE в порядке UUID, промокод — до проверки
счётчика и увеличения current_uses. Частичный уникальный индекс из V2 дополнительно
защищает от двух активных заказов. Время проверки берётся из PostgreSQL через
clock_timestamp() после ожидания блокировки.
См. [блокировки PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html).

`ORDER_CREATE_INTERVAL_MINUTES` задаёт N минут в `.env`; по умолчанию 5.
Допустимы дробные значения, 0 отключает только частотный лимит. После изменения
значения пересоздай api: `docker compose up --build -d api`.
Лимит создания читает только CREATE_ORDER; недавняя UPDATE_ORDER его не блокирует.
При ограничении возвращаются 429 ORDER_LIMIT_EXCEEDED, Retry-After в секундах
и details.retry_after_seconds. Лимит проверяется раньше активного заказа,
поэтому повтор сразу после успешного создания даёт 429, а после N минут — 409,
если заказ всё ещё активен.

Для ручной проверки создай товар под SELLER и скопируй его id. Войди под USER
или ADMIN и вызови `POST /orders`:

```json
{
  "items": [
    {"product_id": "UUID созданного товара", "quantity": 2}
  ]
}
```

В ответе будут id заказа, владелец, позиции, цены на момент заказа, итоговая
сумма и скидка. Необязательный promo_code проверяется по уже существующим
записям в БД, созданным через POST /promo-codes.

## Создание промокода

`PromoCodesApi` реализует сгенерированный `BasePromoCodesApi`. SELLER и ADMIN
вызывают `POST /promo-codes` и получают 201 PromoCodeResponse, USER получает 403.
Сервис повторно проверяет текущую роль в БД в той же транзакции, что и INSERT.
Обе даты должны иметь часовой пояс; valid_until строго позже valid_from.
Ошибки дат — 400 VALIDATION_ERROR с указанием полей.

`PromoCodesRepository` выполняет параметризованный INSERT RETURNING. UUID и
current_uses=0 назначаются БД, active по умолчанию true. Промокоды глобальные,
без seller_id. Можно создать неактивный, будущий или уже истёкший промокод;
его пригодность для заказа проверяется при применении. max_uses ограничен
диапазоном INTEGER: 1..2147483647. Деньги сохраняются точно через Decimal.

Уникальность обеспечивает ограничение PostgreSQL. INSERT ON CONFLICT (code)
DO NOTHING возвращает отсутствие строки, которое преобразуется в 409
PROMO_CODE_ALREADY_EXISTS. Даже конкурентные запросы не создают два одинаковых
кода и не сбрасывают current_uses уже существующего промокода. Другие ошибки БД
остаются INTERNAL_ERROR. Проверка ответа выполняется до commit, поэтому при
поздней ошибке новая строка откатывается. Миграции менять не требуется.

## Защита от конкурентных запросов

Порядок получения блокировок для операций с заказами закреплён в
`OrdersRepository`: **пользователь → существующий заказ → товары по UUID → промокод**.
Создание пропускает блокировку заказа, поскольку он ещё не существует.
Все блокировки берутся через одно соединение внутри транзакции; commit или
rollback освобождает их. См. [блокировки строк PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

`OrdersService.locked_transaction(subject, order_id=None)` — общая граница
транзакции для создания, чтения, обновления и отмены. Если передан order_id, контекст
блокирует пользователя и заказ через FOR UPDATE, затем проверяет роль и владельца.
ADMIN может получить контекст чужого заказа; USER получает
ORDER_OWNERSHIP_VIOLATION, SELLER — ACCESS_DENIED. Несуществующий заказ даёт 404.

PUT читает старые позиции через get_items и блокирует объединение старых и новых
product_id через lock_products. Отмена блокирует все старые товары. Связанный
промокод блокируется последним через lock_promo_by_id. Проверки состояния и
лимита конкретной операции выполняются в этой же транзакции. GET держит
блокировку родительского заказа до чтения позиций, поэтому не смешивает данные
до и после конкурентного обновления.

lock_products сортирует и убирает повторы в списке блокируемых UUID.
Резервирование также выполняет обновления в порядке UUID. На уровне SQL
есть дополнительные предикаты stock >= quantity и current_uses < max_uses.
Если предикат не прошёл после бизнес-проверок, операция считается нарушением
внутреннего инварианта и откатывается целиком. Ограничения CHECK и частичный
уникальный индекс V2 дополнительно защищают БД.

Повторяющиеся product_id в запросе **отклоняются с 400**, позиции не объединяются.
Проверка есть в сгенерированной модели и на входе сервиса: даже если внутренний
код изменит список DTO после его создания, двойного резервирования не будет.

`test_order_locks_postgres.py` намеренно удерживает блокировку в одном соединении
и запускает операцию в другом. Через pg_stat_activity и
[pg_blocking_pids](https://www.postgresql.org/docs/17/functions-info.html#FUNCTIONS-INFO-SESSION-TABLE)
тест убеждается, что второй запрос ожидает именно нужную блокировку. После
освобождения проверяются актуальные остатки, состояние заказа и счётчик промокода.
Есть проверки отката и освобождения блокировок, уникального индекса, а также
восьми параллельных покупателей с ограниченным складом или промокодом.

## Обновление, отмена и состояния заказа

`PUT /orders/{id}` принимает только новый массив items и возвращает 200 с
OrderResponse. USER работает со своим заказом, ADMIN — с любым. Проверки идут
в порядке: владелец → CREATED → частотный лимит UPDATE_ORDER → возврат старых
остатков → проверка и резервирование нового состава → пересчёт → запись
UPDATE_ORDER. При проверке остатков учитываются возвращённые единицы этого же
заказа. Идентификатор, владелец и created_at сохраняются, updated_at меняет БД.

При любом сбое откатываются старые и новые остатки, позиции, суммы, промокод и
журнал. Даже ошибка БД после удаления старых позиций восстанавливает их.
Каждый явный PUT создаёт новые снимки из текущих цен заблокированного каталога,
включая товары, уже присутствовавшие в заказе. Обычное изменение цены каталога
снимки существующего заказа не меняет; это проверяется через GET.

Промокод через PUT передать или заменить нельзя. Для уже связанного промокода:

- повторно проверяются active, период действия и лимит с учётом собственного
  использования заказа; достижение max_uses этим заказом не мешает обновлению;
- при сохранении скидки current_uses не увеличивается; сумма и скидка
  пересчитываются через Decimal с ROUND_HALF_UP;
- если сумма до скидки ниже min_order_amount, связь обнуляется, скидка становится
  нулевой, current_uses уменьшается один раз. Последующее увеличение суммы
  автоматически промокод не возвращает;
- истёкший, ещё не начавшийся или отключённый промокод даёт 422 PROMO_CODE_INVALID
  и полный откат, в том числе когда новая сумма ниже минимума.

`ORDER_UPDATE_INTERVAL_MINUTES` в `.env` задаёт лимит UPDATE_ORDER, по умолчанию
5 минут. Значение 0 отключает этот частотный лимит. CREATE_ORDER и UPDATE_ORDER
проверяются независимо по текущему пользователю sub; действие ADMIN над чужим
заказом записывается на ADMIN. Для применения настройки пересоздай api:
`docker compose up --build -d api`. Неудачные попытки в журнал не попадают.

`POST /orders/{id}/cancel` разрешён только для CREATED и PAYMENT_PENDING.
Он возвращает все зарезервированные единицы, освобождает одно использование
связанного промокода и устанавливает CANCELED в одной транзакции. Срок и active
промокода отмене не мешают. Ответ — 200 OrderResponse; исторические позиции,
цены, ссылка на промокод и суммы сохраняются. Повторная отмена возвращает
409 INVALID_STATE_TRANSITION и ничего повторно не возвращает. Отдельного
частотного лимита и записи CANCEL_ORDER нет: такой тип операции заданием
не предусмотрен.

Допустимые переходы собраны в `app/services/order_states.py`:

```text
CREATED → PAYMENT_PENDING → PAID → SHIPPED → COMPLETED
   ↓             ↓
 CANCELED      CANCELED
```

Редактирование состава разрешено только в CREATED. Самопереходы, выходы из
терминальных состояний и остальные пары запрещены. Дополнительных публичных
маршрутов оплаты и доставки нет; тесты проверяют все 36 пар состояний.

### Демонстрационные заказы в остальных состояниях

После создания demo-аккаунтов через scripts/seed.ps1 выполни из `hw2`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\seed-order-states.ps1
```

Команда создаёт для demo_user пять заказов: PAYMENT_PENDING, PAID, SHIPPED,
COMPLETED и CANCELED, и печатает их UUID. Каждый содержит одну единицу отдельного
демонстрационного товара demo_seller. Для CANCELED склад уже возвращён.
CREATED можно получить обычным POST. Если у пользователя уже есть активный
заказ, сначала отмени его; иначе команда завершится без изменений. После
демонстрации отмени PAYMENT_PENDING, чтобы снова создавать заказы.

Повторный запуск сохраняет существующие заказы и их текущие состояния, цены,
остатки, не резервирует товар повторно и не восстанавливает уже отменённый
заказ. Начальные данные создаются только этой явной командой. При необходимости
можно указать другие существующие аккаунты через -Buyer и -Seller.

`test_order_mutations_postgres.py` проверяет права, все состояния, снимки цен,
отдельный лимит UPDATE_ORDER, снятие скидки и полный откат при ошибках. Гонки
проверяют две отмены, два обновления одного пользователя, USER против ADMIN,
обновление одновременно с отменой и замену товаров в разных заказах. SQL-проверки
подтверждают сохранение общего количества товара и однократное освобождение
промокода. Демонстрационные данные проверяются на повторный и конкурентный запуск.

## JSON-логирование запросов

`app/middleware/request_logging.py` записывает один JSON-объект в stdout после
каждого HTTP-запроса, включая health, Swagger, неизвестные маршруты, ошибки
валидации, 401, 403 и 500. Каждое событие занимает одну строку. Поля:

| Поле | Значение |
| --- | --- |
| request_id | Новый UUID v4, совпадает с X-Request-Id в ответе, включая 500. |
| method | HTTP-метод. |
| endpoint | Путь запроса без query string. |
| status_code | HTTP-код ответа. |
| duration_ms | Длительность в миллисекундах по монотонному таймеру. |
| user_id | UUID после успешной проверки access JWT и пользователя в БД; иначе null. |
| timestamp | Время начала запроса в ISO 8601, UTC с суффиксом Z. |
| body | Маскированное тело для POST, PUT, PATCH и DELETE; пустое тело — null. |

Например, успешный вход:

```json
{"request_id":"77777777-7777-4777-8777-777777777777","method":"POST","endpoint":"/auth/login","status_code":200,"duration_ms":42.718,"user_id":null,"timestamp":"2026-10-22T12:00:00.000Z","body":{"username":"demo_user","password":"***"}}
```

Вход, регистрация и refresh — публичные методы: access JWT в них не проверяется,
поэтому user_id равен null. У защищённого маршрута отказ по роли 403 сохраняет
идентификатор уже проверенного пользователя. Невалидный, истёкший JWT или токен
с устаревшей ролью не используются как источник user_id. Входящий X-Request-Id
также не используется: каждый запрос получает новый идентификатор сервера.

Пароли, токены, API-ключи, секреты, credentials, cookie и другие чувствительные
поля заменяются на `***` рекурсивно, включая массивы. Регистр и разделители в
именах ключей не мешают маскированию. Bearer-строки и JWT маскируются и в обычных
строковых полях. Заголовки Authorization/Cookie, query string и тела ответов
в журнал запросов не записываются.

Для тела действует лимит захвата 64 КиБ: он покрывает максимальный допустимый
товар с длинными строками Unicode. При превышении в body записывается
`{"omitted":"body_too_large","limit_bytes":65536}`. Повреждённый JSON получает
метаданные invalid_json, остальные типы содержимого — unsupported_media_type.
Их сырое содержимое не выводится: надёжно замаскировать в нём секреты нельзя.
Ограничение относится к журналу: обработчик получает всё исходное тело без
изменений, в том числе при передаче частями. Денежные числа логируются точно,
без преобразования Decimal во float.

Неожиданные ошибки дополнительно создают JSON-событие server_error с тем же
request_id, классом исключения и местами в стеке. Текст исключения, SQL,
параметры запросов и локальные переменные не печатаются. Стандартный текстовый
access-log Uvicorn в Docker отключён; запросы записывает этот middleware.

После обновления из `hw2`:

```powershell
docker compose up --build -d api
docker compose logs -f --no-log-prefix api
```

Скопируй X-Request-Id из ответа и найди связанные записи:

```powershell
docker compose logs --no-log-prefix api | Select-String -SimpleMatch "UUID из X-Request-Id"
```

`tests/test_request_logging.py` проверяет обязательные поля и корреляцию ответов,
ошибки, реальные JWT и роли, маскирование секретов, конкурентные запросы,
повторное чтение тела, передачу частями и ограничение размера журнала.

## Проверки

Запуск проверок из `hw2`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test.ps1
```

Эквивалентная команда:

```powershell
docker compose --profile tools run --build --rm test
```

Тестовый образ генерирует API заново при сборке и запускает pytest. Проверки
контракта используют тестовые реализации API. В `test_products.py` проверяются
настоящие `ProductsApi` и `ProductsService`, роли и транзакционные границы,
а репозиторий подменяется хранилищем в памяти. База данных для этого запуска
не нужна; тесты PostgreSQL без `TEST_DATABASE_URL` пропускаются.

В `test_order_contract.py` проверяются ограничения позиций и настройка N.
В `test_auth.py` используются настоящие JWT, Argon2 и сервисы авторизации/товаров;
подменяется только хранилище БД. Проверяются сроки и назначения токенов, подписи,
обязательные claims, смена роли, владение товаром и запрет повышения привилегий.

Для проверки настоящих SQL-запросов, сохранения денег, `RETURNING`, триггера,
отката, мягкого удаления и JWT с БД запусти из `hw2`:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-integration.ps1
```

Эквивалентная команда:

```powershell
docker compose --profile tools run --build --rm test-integration
```

Она запускает отдельную `db-test` без внешнего порта и постоянного тома,
применяет те же миграции через `flyway-test` и выполняет
`test_products_postgres.py`, `test_auth_postgres.py`, `test_orders_postgres.py`,
`test_order_locks_postgres.py`, `test_order_mutations_postgres.py`
и `test_promo_codes_postgres.py`. В первом файле подменяется
только JWT-зависимость; во втором используются настоящие JWT без подмены
авторизации, включая конкурентную регистрацию. После архивации тест читает строку напрямую
через SQL и убеждается, что статус равен ARCHIVED, а строка сохранилась.
Данные основного сервиса `db` эти тесты не используют.

Тесты заказов проверяют порядок ошибок, все проблемные остатки, снимки цен,
ROUND_HALF_UP, границы и лимит промокода, переполнение сумм и полный откат
после поздней ошибки. Параллельные HTTP-запросы проверяют одного пользователя,
последний товар, последнее использование промокода и обратный порядок позиций.

Полный набор тестов с PostgreSQL в Docker:

```powershell
docker compose --profile tools run --build --rm test-integration python -m pytest -q
```

Остановить только тестовую БД после проверки:

```powershell
docker compose stop db-test
```
